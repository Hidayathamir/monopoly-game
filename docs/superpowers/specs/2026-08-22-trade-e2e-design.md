# Trade Feature E2E Tests — Design

## Assumptions (author was unavailable — please verify)

1. **Feature under test**: the multiplayer trade feature — `ProposeTrade`,
   `AcceptTrade`, `RejectTrade`, `CancelTrade` — gated by the server env flag
   `TRADES_ENABLED` (server-side, per-room; propagated to clients through
   `GameState.tradesEnabled`). Default disabled; anything other than the literal
   `true` disables it for every room.
2. **Tests should exercise both flag states**: (a) a regression test proving the
   flag-off UI hides all trade affordances, and (b) the full propose → accept /
   reject / cancel flows on a server launched with `TRADES_ENABLED=true`, plus
   the bot auto-decision path (proposing to a bot seat).
3. **Server fixture strategy**: the existing worker-scoped `serverUrl` fixture
   spawns a server without `TRADES_ENABLED`. A second worker-scoped fixture
   `serverUrlTrades` spawns a server on a different port
   (`4100 + workerIndex`) with `TRADES_ENABLED=true`. Worker-scoped fixtures are
   lazy — only specs that use `serverUrlTrades` pay for the second server, and
   other specs are unaffected.
4. **Determinism via the seeder**: the trade UI is only reachable mid-game and
   requires a known turn order + property ownership. Following the established
   pattern (bankruptcy/monopoly-rent seeds), the decision point is seeded with a
   full `GameState` via `POST /seed` (`E2E_SEED_ENABLED=true` is already set by
   `e2e/helpers/server.ts`). `server/gameServer.ts::seedState` preserves the
   room's own `tradesEnabled` over the seed's value, so the same seed file works
   on both flag-on and flag-off servers.
5. **New generated fixtures** `e2e/fixtures/trade-seed.ts` (2 humans) and
   `e2e/fixtures/trade-bot-seed.ts` (human + bot) produced by one new script
   `scripts/print-trade-seed.ts` + `npm run print-trade-seed`, following the
   checked-in generated-fixture convention (pure literals, only
   `import type { GameState }`, `// GENERATED by ...` header).
6. **One small production change for testability**: add `data-testid="trade-offer"`
   to the offer card in `TradeInboxModal.tsx` so the Cancel test can target the
   offer's Cancel button unambiguously (the modal footer also has a Cancel
   button). This matches the repo's widespread `data-testid` convention.

## Background

- **Reducer** (`src/logic/gameReducer.ts`):
  - `ProposeTrade`: gated on `state.tradesEnabled`; requires the offerer to own
    every offered space unmortgaged with no houses; appends a `PendingTrade` with
    an auto-incremented id (logging `TradeProposed`), OR — when the target is a
    bot / bot-controlled — immediately resolves via `shouldAcceptTrade`
    (`src/logic/bot.ts`: received value ≥ given value, priced at board price).
  - `AcceptTrade` (gated): validates via `isTradeValid` (ownership, no mortgage,
    no houses, sufficient cash) then `applyTrade` swaps owners, cash, and
    `properties` lists; removes the trade; logs `TradeAccepted` (or
    `TradeRejected` when the offer became invalid).
  - `RejectTrade` / `CancelTrade` (gated): remove the trade and log
    `TradeRejected` / `TradeCancelled`.
- **Server** (`server/gameServer.ts`):
  - `handleAction` rejects the four trade actions with an error when
    `!state.tradesEnabled`.
  - `ProposeTrade` is accepted from the `offer.fromId` slot (no turn requirement);
    `AcceptTrade`/`RejectTrade` from the `toId` slot; `CancelTrade` from the
    `fromId` slot. `seedState` overwrites the incoming state's `tradesEnabled`
    with the room's own value.
- **Client**:
  - `GameView.tsx`: `canTrade = tradesEnabled && isMyTurn && phase === Waiting &&
    !pendingAction`; renders `TradeModal` when a target is picked and
    `TradeInboxModal` when opened.
  - `PlayerCard.tsx`: hover popup shows a `🤝 Trade` button
    (`t('action.trade')`) when `tradesEnabled` and the card isn't the current
    player; disabled when `!canTrade`.
  - `Sidebar.tsx`: a `Trades` (inbox) button (`t('trade.inbox')`) shown only when
    `tradesEnabled`, with a badge of relevant pending trades.
  - `TradeModal.tsx`: two columns (offer / request) with a money number input and
    one checkbox per eligible property (owned, unmortgaged, no houses). `Propose`
    button builds the `TradeOffer`.
  - `TradeInboxModal.tsx`: renders each pending trade with `Accept`/`Reject`
    (for `toId`) and `Cancel` (for `fromId`); `No pending trade offers` when
    empty.
- **i18n (en)** (`src/i18n/locales/en/translation.json`): `action.trade` =
  "🤝 Trade", `trade.inbox` = "Trades", `trade.propose` = "Propose",
  `trade.accept` = "Accept", `trade.reject` = "Reject", `trade.cancel` =
  "Cancel", `trade.noOffers` = "No pending trade offers", and log keys
  `event.tradeProposed` = "{{from}} proposed a trade to {{to}}",
  `event.tradeAccepted` = "{{from}} and {{to}} completed a trade",
  `event.tradeRejected` = "{{to}} declined {{from}}'s trade offer",
  `event.tradeCancelled` = "{{from}} cancelled their trade offer to {{to}}". All
  keys already exist in both locales — no new strings.
- **Money formatting** (`src/data/currency.ts`): compact; USD `1100` → `$1.1K`,
  `1300` → `$1.3K`, `0` → `$0`, `100` → `$100`.
- **Board cells** (`BoardGrid.tsx`): owner stripe is the `div.absolute` at the
  bottom of the cell with an inline `backgroundColor` = owner color
  (`#E74C3C` → `rgb(231, 76, 60)` Alpha, `#3498DB` → `rgb(52, 152, 219)` Bravo,
  `#2ECC71` → `rgb(46, 204, 113)` Droid). Board names (en):
  `board.space.1` = "Salvador", `3` = "Rio", `5` = "TLV Airport", `6` = "Tel
  Aviv", `9` = "Jerusalem".

## Design

### 1. Test-server fixture — `e2e/fixtures.ts`

Add a second worker-scoped fixture next to `serverUrl`:

```ts
interface WorkerFixtures {
  serverUrl: string
  serverUrlTrades: string
}

// ...
serverUrlTrades: [
  async ({}, use, workerInfo) => {
    const server = await startServer(4100 + workerInfo.workerIndex, { TRADES_ENABLED: 'true' })
    await use(server.url)
    server.close()
  },
  { scope: 'worker' },
],
```

Port `4100 + workerIndex` cannot collide with the existing `4000 + workerIndex`.
`startServer` already merges env (`E2E_SEED_ENABLED: 'true'` stays on).

### 2. Generator script — `scripts/print-trade-seed.ts`

Semicolons, modeled on `scripts/print-bankruptcy-liquidation-seed.ts`. Writes
both fixtures:

- `e2e/fixtures/trade-seed.ts` — 2 players, `tradesEnabled: true`:
  - Alpha (id 0, `$1200`, current player, `turnOrder [0, 1]`, `phase: waiting`):
    owns Salvador (1), Rio (3), TLV Airport (5).
  - Bravo (id 1, `$1200`): owns Tel Aviv (6), Jerusalem (9).
- `e2e/fixtures/trade-bot-seed.ts` — 2 players, `tradesEnabled: true`:
  - Alpha (id 0, `$1200`, current player): owns Salvador (1), Rio (3),
    TLV Airport (5).
  - Droid (id 1, `isBot: true`, `$1200`): owns Tel Aviv (6).

`createSeededState` derives `properties` lists from the board overrides and
defaults `passedGo` to `true`, so a `Waiting`-phase seed validates cleanly
(`validateStateStructure`: `Waiting` requires `pendingAction === null` and
`dice === null`). Add npm script `print-trade-seed`.

### 3. E2E spec — `e2e/trade.spec.ts`

No semicolons (matches `e2e/*`). A local `joinRoom` helper replicates the
two-context room setup from the other server-backed specs. Five tests:

**Test 1 — feature flag off (uses `serverUrl`):**
Seed `tradeSeed` on a default (trades-disabled) server; the room's own
`tradesEnabled` overrides the seed to `false`. Assert:
- Sidebar has no `Trades` inbox button.
- Hovering Bravo's player card shows the popup without a `🤝 Trade` button.

**Test 2 — propose → accept (uses `serverUrlTrades`):**
- Alpha (current) hovers Bravo's card → popup → `🤝 Trade` → `TradeModal`.
- Offers Rio (3) + `$100` cash, requests Tel Aviv (6). Propose.
- Alpha log: "Alpha proposed a trade to Bravo".
- Bravo's `Trades` sidebar button shows badge `1`; opening the inbox shows the
  offer (`You offer: Rio + $100`); Bravo clicks `Accept`.
- Inbox shows `No pending trade offers`; both logs show "completed a trade".
- Money: Alpha `$1.1K` (1200−100), Bravo `$1.3K` (1200+100).
- Ownership stripes: `board-cell-3` → Bravo (`rgb(52, 152, 219)`),
  `board-cell-6` → Alpha (`rgb(231, 76, 60)`).
- Bonus gate check: before Alpha proposes, Bravo's own card popup shows a
  *disabled* `🤝 Trade` button (trade requires the proposer's turn).

**Test 3 — reject (uses `serverUrlTrades`):**
Same propose as Test 2; Bravo opens the inbox and clicks `Reject`. Inbox shows
`No pending trade offers`; Bravo log: "declined Alpha's trade offer";
`board-cell-3` still Alpha's stripe (`rgb(231, 76, 60)`).

**Test 4 — cancel (uses `serverUrlTrades`):**
Alpha proposes, then opens his own `Trades` inbox (badge `1`), clicks the offer's
`Cancel` (scoped via `data-testid="trade-offer"`; the modal footer also has a
Cancel). Inbox shows `No pending trade offers`; Alpha log: "cancelled their
trade offer"; no ownership change.

**Test 5 — bot auto-decision (uses `serverUrlTrades`, single page):**
Host adds a bot (`Droid`) in the lobby, seeds `tradeBotSeed`, proposes TLV
Airport (5, `$200`) for Tel Aviv (6, `$100`) to Droid. `shouldAcceptTrade`
(200 ≥ 100) accepts immediately. Assert: log "Alpha and Droid completed a
trade"; `board-cell-5` stripe → Droid (`rgb(46, 204, 113)`); `board-cell-6`
stripe → Alpha; no pending trades (opening the inbox shows
`No pending trade offers`).

### 4. Testability hook — `src/components/Modals/TradeInboxModal.tsx`

Add `data-testid="trade-offer"` to the offer-card `<div>` (the `bg-bg-darker`
row). One-line change; enables Test 4's unambiguous Cancel click.

### 5. Docs — `AGENTS.md`

Add a sentence documenting the `serverUrlTrades` fixture (port
`4100 + workerIndex`, `TRADES_ENABLED=true`) beside the existing `serverUrl`
line, so future specs know trade-capable specs must use it.

## Verification

1. `npm run print-trade-seed` → writes both fixtures.
2. `npm run typecheck` → passes (all 3 TS projects).
3. `npm run lint` → passes.
4. `npm run test:unit` → passes (no unit tests affected; `TradeInboxModal` change
   is a pure attribute addition).
5. `npm run build` → produces `dist/` (e2e server fixture requirement).
6. `npx playwright test e2e/trade.spec.ts` → all 5 tests pass.
7. `npx playwright test e2e/monopoly-rent.spec.ts e2e/bankruptcy-liquidation.spec.ts`
   → regression check on the shared fixtures.
8. Flake check: `npx playwright test e2e/trade.spec.ts --repeat-each=3`.

## Out of scope

- No change to the trade feature itself (rules, UI behavior, server gating).
- No unit tests: reducer trade rules are already covered by
  `src/logic/__tests__/gameReducer.test.ts` (per blast-radius data) and the
  modals by `TradeModal.test.tsx` / `TradeInboxModal.test.tsx`; this spec covers
  the full server + UI pipeline.
- No changes to existing e2e specs (the new fixture is additive).
