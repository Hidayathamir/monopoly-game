# Trade E2E Scenario Expansion — Design

## Purpose

Extend `e2e/trade.spec.ts` with deterministic, seeder-driven coverage for the
full trade scenario matrix. The existing spec (committed) covers the happy
path plus flag-off hiding. The working tree adds cash clamping, empty-trade
guard, proposal validation (with the `TradeProposalRejected` event), and four
extra tests. This spec adds the remaining **14 positive + 12 negative**
scenarios the branch owner requested.

## Assumptions (author unavailable — please verify)

1. **Scope**: e2e only, over the real server (`serverUrlTrades`) and real UI.
   No new production behavior changes are needed — every scenario is reachable
   with the existing reducer, server, `TradeModal`, `TradeInboxModal`, and test
   hooks (`data-testid="player-card"`, `board-cell-N`, `sidebar`, `event-entry`,
   `trade-offer`, `room-code`).
2. **Scenario inventory**: the 26 scenarios in the request map 1:1 to new
   tests. Scenarios already covered by committed or working-tree tests are NOT
   duplicated; a few existing tests gain a missing badge assertion instead of a
   new test.
3. **Seed strategy**: follow the established generated-fixture pattern.
   `scripts/print-trade-seed.ts` gains 7 new `createSeededState` scenarios and
   emits 7 new pure-literal fixtures (`import type { GameState }` only, `//
   GENERATED by` header). Tests never hand-edit generated files; they may
   `structuredClone` a generated seed and mutate it for stale-state scenarios
   (already the established pattern in the working tree).
4. **Derived/stale scenarios**: three negatives need a mid-game re-seed between
   modal interaction and `Propose` to bypass client-side guards that would
   otherwise make the server-side rejection unreachable (the modal clamps cash
   to the target's balance and only lists target-owned properties). The
   `TradeModal` keeps its local `useState` across a re-seed, so the pending
   offer values survive to be rejected by `isTradeValid`.
5. **Badge semantics**: `tradeCount` (GameView) counts `pendingTrades` where the
   viewer is `fromId` or `toId`. A neutral third player's count is 0 → no badge
   span renders. Badge asserts use `toContainText('1')` / `not.toContainText('1')`
   on the sidebar `Trades` button.
6. **Cash/format assertions** use compact `Intl.NumberFormat`
   (`src/data/currency.ts`): 1100→`$1.1K`, 1300→`$1.3K`, 1250→`$1.3K`,
   1150→`$1.2K`, 0→`$0`. Numbers are chosen so both endpoints are exact.
7. **Stripes**: Alpha `#E74C3C`→`rgb(231,76,60)`, Bravo/Droid
   `#3498DB`→`rgb(52,152,219)`, Charlie `#2ECC71`→`rgb(46,204,113)`. Droid sits
   at id 1 so it shares Bravo's color (from the generated seed).

## Scenario → test mapping

**Positive (14)**
1. cash-only both directions (`tradeSeed`) — offer $200 / request $100 →
   Alpha `$1.1K`, Bravo `$1.3K`, no stripe change.
2. property-only (`tradeSeed`) — Rio ⇄ Tel Aviv, money unchanged, stripes swap.
3. multi-property both directions (`tradeSeed`) — Salvador+Rio ⇄ Tel Aviv+Jerusalem.
4. railroad + utility (`tradeUtilitySeed`) — TLV Airport ⇄ Power Company.
5. target has exactly enough cash (`tradeCashSeed`) — request exactly $50,
   Bravo ends `$0`, Alpha `$1.3K`.
6. bot accepts at exactly-fair boundary (`tradeBotSeed`) — offer Salvador+$40
   for Tel Aviv (received 100 == given 100).
7. Bravo proposes to Alpha on Bravo's turn (`tradeReverseSeed`).
8. third neutral player sees no badge (`tradeThreeSeed`).
9. two pending offers to two different targets (`tradeThreeSeed`).
10. accepting one leaves the other pending (`tradeThreeSeed`).
11. offerer's inbox shows Cancel; target's shows Accept/Reject (`tradeSeed`).
12. two sequential trades in one game (`tradeSeed`).
13. bot gives a property and receives cash (`tradeBotSeed`) — Alpha offers $150
    for Tel Aviv.
14. bot is on the receiving end of a bargain (`tradeBotSeed`) — Alpha offers
    TLV Airport for nothing.

**Negative (12)**
1. offer cash capped at proposer's cash (`tradeOfferCapSeed`) — type 100 →
   `50`, capped offer transfers.
2. negative cash clamped to 0 (`tradeSeed`) — `-100` → `0` in both fields.
3. request property not owned by target → `event.tradeProposalRejected`
   (`tradeSeed` + re-seed moving Tel Aviv to Alpha).
4. mortgaged property excluded from modal (`tradeMortgageSeed`).
5. houses/hotel excluded from modal (`tradeHouseSeed`).
6. bot rejects an unfair trade (`tradeBotSeed`) — Salvador for Tel Aviv →
   `Droid declined Alpha's trade offer`, nothing changes.
7. propose to a bot that can't afford requested cash → proposal rejected
   (`tradeBotSeed` + re-seed Droid to $100).
8. trade with a bankrupt player blocked (`tradeBankruptSeed`) — Trade button
   disabled.
9. trade with self impossible (`tradeSeed`) — own card shows no Trade button.
10. cancel on an already-accepted trade is a no-op (`tradeSeed`) — after
    acceptance Alpha's inbox is empty, nothing to cancel.
11. inbox badge decrements after accept/reject/cancel — new two-offer badge
    test (2→1→0 via accept then reject) **plus** badge-gone assertions added to
    the existing reject and cancel tests.
12. rejecting removes the offer from both inboxes (`tradeSeed`).

## Implementation notes

- Add a `joinByCode` helper (page, url, code, name) and a `makeBotRoom` helper
  to the spec to support 3-player rooms and reduce the duplicated solo-room
  setup; keep the existing `joinRoom`/`openTradeModal` signatures.
- `getByLabel(name, { exact: true })` resolves the modal's wrapped checkboxes;
  board cells are not labels so no strict-mode clash. Absence asserts:
  `getByLabel('Rio', { exact: true })` → count 0.
- Number inputs: offer is `input[type="number"]` `.nth(0)`, request `.nth(1)`.
- Modal scoping for button contrast: use `[data-testid="trade-offer"]` card,
  never the bare "Cancel" (the modal footer also says Cancel).
- Unit tests: extend `TradeModal.test.tsx` (offer cap, negative clamp,
  mortgaged/houses exclusion) — cheap, fast regression next to the e2e.
- No changes to `src/logic`, `server/`, i18n, or wire contract.
